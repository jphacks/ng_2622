# 採点を定量的にし、AI に頼りすぎないための調査

> 調査メモ（2026-11-16）。決定ではない。どれをやるかは、この後に決める。決めたら ADR に残す。
> きっかけは、Award Day の EXPO でもらった声（[`docs/feedback/20261115-award-day.md`](../../../feedback/20261115-award-day.md) の「採点」）。言われたのは次の 4 つ。
>
> - 採点のロジックを見えるようにしてほしい
> - 定量的で納得できる説明がほしい
> - もっと安いモデルでも採点は組めるはず
> - 端末で文字起こしの性能が違うと不公平
>
> これを受けて、AI に頼りすぎず、性能の低めの AI でも点が安定する形を探した。
> 調べ方: 問いを 6 つに分け、サブエージェントが 1 つずつ Web と repo を調べた。各文書の「担当 N」は、ファイル名の先頭の番号と同じ。途中で、全担当が共有する Web 検索の回数の上限に達した。そのため、原典を開けなかった数字が残っている。その数字は、各文書に「未確認」と書いてある。
> 数字は、どれも出典の条件（話者・課題・データ）でのもの。日本の中高生が 3D の場面を 20 秒で描写したときの値ではない。

## 問いの分け方

採点の流れの段ごとに、6 つに分けた。

| 番号 | 段 | 問い | 文書 |
| --- | --- | --- | --- |
| 1 | 正解の考え方 | 試験の採点者や研究者は、何をどう見ているか。採点のぶれをどう抑えているか | [`1-expert-rubrics.md`](./1-expert-rubrics.md) |
| 2 | 確かめ | 講師が点を付けた公開のデータはあるか。採点の正しさをどう測るか | [`2-benchmarks.md`](./2-benchmarks.md) |
| 3 | 判定（AI なし） | AI を使わず、決まった計算で何を測れるか | [`3-deterministic-metrics.md`](./3-deterministic-metrics.md) |
| 4 | 判定（AI あり） | AI に任せる部分を、安いモデルでも安定させるにはどうするか | [`4-llm-stability.md`](./4-llm-stability.md) |
| 5 | 入力 | 文字起こしの誤りと、端末による差をどう減らすか | [`5-asr-fairness.md`](./5-asr-fairness.md) |

調べたときの採点の形（2026-11-16 の main）:

| 軸 | 重み | 付け方 |
| --- | --- | --- |
| 内容 | 50% | 場面ごとのチェックリストを使う。Claude が項目ごとに「言えた・一部・言えていない」を判定し、描写の正誤も判定する。点は、コードがその判定から F1 で計算する（[ADR](../../../adr/20261110-score-content-with-checklist-f1.md)） |

- 文字起こしは、端末の SpeechAnalyzer で行う。失敗したときは Azure に切り替える。
- 本番のモデルは Sonnet 5.5 の effort low。

## 結論

1. **本番の試験には、生成 AI（LLM）だけで点を決めているものが見つからなかった。**
   - 点は、特徴量から人の点を予測するモデル（これも機械学習）が出す。Versant のように全部を自動で採点する試験や、PTE Academic のように発音と流暢さを自動だけで採点する試験もある（PTE は 2025-08 から、一部の課題で人が内容を採点する）。ただし、多くは、人が確認・混ぜ合わせ・確信の低い答えだけの採点のどれかで関わる。LLM は、問題作り・会話の相手・練習の助言に使われている（6）。
   - 信頼性の示し方は、ほぼ共通している。「人と人の一致」を上限として、機械と人の一致がそれに近いことを示す。目安は次の 3 つ（Williamson, Xi & Breyer 2012。原文は開いておらず、ACT と ETS が引用した値で確かめた。2・6）。
     - QWK か相関が 0.70 以上
     - 人と人の値からの下がり幅が 0.10 以内
     - 平均の差（標準化した値）が 0.15 以内
   - 審査で言われた「定量的で納得できる説明」には、この形でそのまま答えられる。
2. **点のぶれの大きな元は、項目 1 つの判定が割れることにある。**
   - 3 級は満点の重みが 5 しかない。そのため、中心の項目 1 つの判定が変わるだけで、全部言えた答えの内容が 11〜25 点動く（下の「手で計算する例」）。細部の項目なら 5〜11 点。
   - これは尺度の性質で、モデルの性能だけの問題ではない（1・4）。
   - 2026-11-11 の実測（150 回）でも、唯一の不合格は、2 級の長い 1 文が 2 つの項目に当たるのに、片方にしか付かなかった答え（78 点と 85 点）だった。項目 1 つの判定の割れである（[ADR](../../../adr/20261111-count-other-claims-as-bonus-and-require-actions-for-items.md)）。指示を直した後の 90 回は、30 通りすべてで幅が 5 点以内だった（[`backend/README.md`](../../../../backend/README.md) の「チェックリストの採点のぶれを測る」）。
   - 測るなら、点の幅より先に、項目の判定の割れ率を見る。
3. **安いモデルに移せるかどうかは、モデルの大きさより、AI に何を判断させるかの狭さで決まる。**
   - 安いモデルに英作文の総合点を直接付けさせると、人との一致は QWK 0.52〜0.63 だった。人どうしは 0.8〜0.9。
   - 一方、参照つきの狭い yes/no の判定では、小さなモデルでも GPT-4 と同じくらい一致した（QA の答えの正誤の判定で κ 0.73〜0.90。4）。
   - このアプリは、AI が判定し、コードが F1 を計算する形を既に取っている。次の一歩は、判定を項目ごとの決まった欄と小さな yes/no に分け、「言えた / 一部」をコードの表で決めることになる（4 の案 A・B）。
4. **内容の数え方には、30 年前からある先例がある。**
   - 失語症の評価の main concept（Nicholas & Brookshire 1995）は、絵の要点の一覧を「正しく全部・正しいが一部・誤り・無い」で判定する。アプリのチェックリストとほぼ同じ形で、採点者どうしの一致は 86〜97%（1）。
   - アプリに足せる工夫は 3 つ。
     - 欠けてはいけない語を決めておく
     - 項目ごとに答えの例を付ける
     - 迷う場合の規則を書く
   - 場面の JSON と文から取り出した組を照らし合わせれば（SPICE の考え方）、AI なしでも判定できる。試作では、役割の取り違えは一致 0（正しい描写に数えない）にできたが、言い換えは落とした（3）。
5. **AI を使わない計算にすぐ置き換えられるのは、流暢さと「級のねらいの形」の 2 つ。**
   - 流暢さ: 今呼んでいる Azure の応答に単語の時刻が入っているが、今のコードは使っていない。その時刻から出せる 1 分あたりの語数と、続けて言えた語数は、人の流暢さの評価と r = 0.76・0.72（22 研究のメタ分析）。追加の費用はかからない（3）。
   - 級のねらいの形: be + -ing・because・so・to + 原形を使えた数と、正しく使えた数は、規則で数えられる（3）。
   - 点にしない指標は 3 つ（3）。
     - 語彙の多様さ: 20 語前後では短すぎる。
     - 語彙のレベル: 作り置きの 48 場面の模範文で測ると、場面の名詞に引きずられ、級の差が出なかった（生徒の発話では未確認）。
     - 統語の比率: 節の切れ目の推定に左右される。
6. **公平さを増やすのにいちばん効くのは、全員の音声を、同じサーバーの同じ設定で文字にすること。**
   - 今の作りには、端末で採点の道筋が変わる所が 3 つある（5）。
     - 端末で文字起こしできない機種と時間切れのときだけ、Azure の文字起こしになる
     - そのとき、Azure の発音評価の方式も変わる
     - サーバーは、端末が送った文字起こしをそのまま信じている
   - ほかに効くもの: 聞き取りに自信の無い語を減点の根拠にしない規則（確信度と音の近さ。5）と、確信が低いときは点を「参考」として出す運用（6）。
7. **temperature や seed では、点を決まったものにできない。**
   - Sonnet 5.5 と Haiku 5.5 は、temperature・top_p・top_k を既定と違う値にすると 400 になる。API の版 2026-10-21 では、どのモデルでも送っただけで 400 になる。seed は無い（4。Claude API の資料でも確かめた）。
   - 点を安定させるのは設計の側。選択肢を減らす、多数決をとる、同じ入力の結果を残しておく。
8. **このアプリの課題にそのまま合う公開データは無い。**
   - 本命は、自分たちで作る小さな正解のデータ（6 場面 × 20 答え ≒ 120 件を、2 人が別々に判定する）。
   - 補助に使えるのは次の 3 つ（2）。ライセンスは、使う前にもう一度確かめる。
     - NICT JLE: 日本人 1,281 人の面接式テストの書き起こしで、絵の描写を含む。9 段階のレベルは面接全体に 1 つで、絵の描写だけの点ではない。成人が多い（16〜18 歳は 92 人）。CC BY-SA 3.0
     - SAILS: 中心の出来事と正誤を 0/1 で付けたもの。人どうしの κ は 0.74 を超える。GPL-3.0
     - Speak & Improve: 非商用の研究だけ

今は勧めないもの（理由は各文書）:

- 文法の誤りを自動で数える（GEC と ERRANT）: 話し言葉では、見つけられる誤りの割合が 0.08 しかない（Speak & Improve 2025 の基準のシステムでの値。3）。
- 語彙の多様さ・語彙のレベル・統語の比率を点にする: 理由は結論の 5（3）。
- 文字起こしのモデルのファインチューン: 力の低い人の誤りが、かえって増えた例がある（5）。
- 汎用の評価モデル（Prometheus 2 など）を入れる: 人との一致が GPT-4 より低い（4 の案 J）。
- 採点専用に蒸留・学習したモデル: 後回しにする。約 1,000 件の学習データで人並みになった例はある。ただし、場面が増え続ける形では場面をまたぐ学習データが要るうえ、モデルを動かす場所も要る（4 の案 I）。
- 部品の名前を、認識のヒントとして渡す: 言っていない語まで認識される水増しの率を、測ってから考える（5）。

力の差がある人どうしで競う指標（Award Day の声の、家族で Duolingo の話）は、採点とは別の話として 6 の案 6 にまとめた。

## 手で計算する例

内容の点は F1 = 2PR / (P + R) × 100。

- R（言えた割合）= 言えた項目の重みの合計 ÷ 満点の重み。言えたは 1 倍、一部は 0.5 倍で数える。
- P（正しさ）= 正しい描写の数 ÷ 言った描写の数。

**3 級で、中心の項目 1 つの判定が変わると何点動くか。** 3 級の項目は、中心 2 つ（重み 2 ずつ）と細部 1 つ（重み 1）で、満点の重みは 5。全部言えた答えから数える。言った描写は全部正しい（P = 1）とし、一覧に無い正しい描写（その他。おまけで足される）は 0 件とする。

| 判定 | R | F1 |
| --- | --- | --- |
| 全部言えた | 5/5 = 1.0 | 2·1·1.0/(1+1.0) = 1.00 → 100 点 |
| 中心の 1 つが「一部」 | (1 + 2 + 1)/5 = 0.8 | 2·1·0.8/1.8 = 0.889 → 89 点 |
| 中心の 1 つが「言えていない」 | (2 + 1)/5 = 0.6 | 2·1·0.6/1.6 = 0.75 → 75 点 |

同じ答えでも、AI の判定が「言えた」と「一部」のあいだで割れるだけで 11 点、「言えていない」まで割れれば 25 点動く。細部の項目（重み 1）なら、R が 0.9 か 0.8 になり、95 点か 89 点（5 点か 11 点）。部分点の答えから数えると動きはもっと大きく、4 の表では 89 点から 14 点・32 点動く。

**girl が car と文字起こしされたとき。** 「A girl is running.」を含む 3 つの描写で、全部の項目を言えていたとする。car と聞き違えられると、女の子の中心の項目（重み 2）を落とすので、R = 3/5 = 0.6 になる。「車が走っている」は場面に無いので誤りになり、P = 2/3 になる。

F1 = 2 × (2/3) × 0.6 / (2/3 + 0.6) = 0.8 / 1.267 = 0.632 → 63 点。

1 語の聞き違いで、100 点が 63 点になる（5）。

**多数決で割れが減る割合。** ある項目で、1 回の判定が少ない方の答え（たとえば、ふだんは「言えた」なのに「一部」）になる確率を p = 0.2 とする。判定どうしは独立だとする。

- 3 票: 多数決の結果が少ない方になるのは、2 票以上が少ない方になったとき。3p²(1 − p) + p³ = 0.096 + 0.008 = 0.104（約 10%）。
- 5 票: 3 票以上が少ない方になったとき。10p³(1 − p)² + 5p⁴(1 − p) + p⁵ = 0.0512 + 0.0064 + 0.0003 ≒ 0.058（約 6%）。

実際には、同じ答えの判定どうしは相関するので、効き目はこれより小さい。また、多数決で減るのは割れだけで、判定の偏り（いつも同じ向きに誤ること）は直らない（4）。

**費用。** 100 万トークンあたり（入力 / 出力）で、Haiku 5.5 は 0.10 / 0.50 USD、Sonnet 5.5 は 2.00 / 10.00 USD。
- 単価はちょうど 1/20 なので、単価だけで見れば、Haiku で 5 票とっても Sonnet 1 回の 1/4 で済む。
- 実際は思考の分で差が縮む。場面の生成の実測（PR #144）では、Haiku の費用は Sonnet の約 1/7 だった。その比なら、5 票で Sonnet 1 回の約 5/7 になる（4 の費用の見積もりの「Sonnet 1 回と同じかそれより安い」）。
- 本番の Sonnet は effort low で、Haiku 5.5 の effort の既定は medium。

## 残る問い

- **未確認の数字**: Web 検索の上限で原典を開けなかったものは、各文書の「不確かな点」に一覧がある。たとえば、Kaggle の上位の点、RubricEval、Mizumoto & Eguchi の QWK、Pearson と Linguaskill の一部、Koenecke 2020。
