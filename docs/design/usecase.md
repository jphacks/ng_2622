## 作品名（仮、2026-10-24）

ScenEnglish（シーングリッシュ）。Scene と English を合わせた造語。読みを「シングリッシュ」にしないのは、シンガポールの英語（Singlish）と紛れるため。MTG で確定させる。

- 似た名前（2026-10-24 に Web 検索）: 「ScenEnglish」と完全に同じ名前のアプリは見つからなかった。近いものに、写真から英単語を出す英語学習アプリ「Scene English」（App Store）と、場面を作って会話を練習する「SceneLingo」がある。

## 目的

全員が同じ 3D シーンを**同時に**見て、各自の解釈で英語で描写し、その発話を AI が判定して競う。

## 動機（2026-10-24）

- 課題: 英語を「話す」機会が足りない。単語帳でどれだけ覚えても、実際に使う機会がない。既存の英会話アプリは決まった文（定型文）を練習するもので、面白みに欠けてモチベーションが続かない。友達と同時に遊ぶゲームにして、自分の言葉で話す量を増やす。
- 面白さ: 同じものを見ても、人によって見方と言い方が違う。その違いを比べる面白さを英語でやる（作品の核）。
- 学びの中身: 見たものを英語で説明する力（描写力）。試験や実際の会話で求められるのに、練習して点数で振り返れる場が少ない。

## 決まったこと

- 全員が同時にプレイする。順番には遊ばない。
  - 理由: 順番に遊ぶと、後の人は前の人の発話を聞いて真似でき（バイアス）、後の人ほど有利になる。
- 各プレイヤーは自分のスマホで遊ぶ。スマホに 3D モデルを表示し、それを見ながらスマホに向かって話す。結果もそのスマホに出る。
- ホログラムは作らず、各自の端末で 3D モデルを表示する形で固定する（2026-10-21）。できそうなら後でホログラムを足す。
  - 理由: 解像度などの見え方をチームで把握できておらず、うまくいくか分からない。ホログラム版を並行して作るのは手間の割に無駄になりやすい。
  - 足す場合は、真ん中に置いた iPad をホログラム表示専用にし、全員で見る共有画面（ルーム画面）もそのとき改めて検討する。
- 全員で見る共有画面（ルーム画面）は当面持たない（2026-10-21）。全員が同じプレイヤー画面を使う。
- 端末どうしをつなぐ「部屋」の仕組みは残す（2026-10-21）。1 人がアプリで部屋を作ってコード（または QR）を出し、他の人はそれで入る。シーンの選択とスタートは部屋を作った人が行う（作り置きの場面に入れ替えたあとは、難易度だけを選ぶ。[`scene-protocol.md`](./scene-protocol.md)）。結果の画面では、自分と相手の描写と点数を並べて見られる。画面の流れは [`screen-flow.md`](./screen-flow.md)。
- 技術スタック: フロントエンドは SwiftUI のネイティブアプリ、バックエンドは TypeScript の API（2026-10-21）。ADR: [`20261021-adopt-swiftui-app-and-cloudflare-workers-backend`](../adr/20261021-adopt-swiftui-app-and-cloudflare-workers-backend.md)。

| 画面 | 端末 | 役割 |
| --- | --- | --- |
| プレイヤー画面 | 各自の iPhone（SwiftUI アプリ） | 3D 表示、録音、結果 |
| ホログラム画面（できそうなら） | 真ん中の iPad | 3D のホログラム表示だけ |

- 本番で使う iPhone: 可能なら 2 台で 2 人が同時にプレイする。無理なら有料アカウントの持ち主の iPhone 1 台だけにする。「無理なら」は、2 台を同時に始める仕組みが間に合わない場合と解釈している（推測）。
- アプリの入れ方: 有料アカウント（個人の登録）の持ち主が、本番の iPhone に Xcode から直接入れる。
- Hack Day の MVP には、最初から 2 台の同時プレイを入れる（2026-10-21）。作品の核である「同時に解釈を比べる」を最初から見せるため。間に合わないときは、下の 1 台のときの見せ方で発表する。
- 基本は複数人で同時にプレイする方向で作る。1 台だけになったときは、1 人がその場でプレイし、結果の画面に事前に録っておいたチームメンバーの回答とその点数を並べて比べる。事前の録音は各自が別々に録るので、真似の問題は起きない。

## 遅れたときに削る順番（2026-10-21 に決定）

演出や便利な機能から削り、同時プレイは最後に削る。作品の核（同じ場面を見て描写し、比べる）を最後まで守るため。

1. QR の読み取り（部屋のコード入力だけにする）
2. シーンのサムネイル（名前の一覧だけにする）
3. 結果発表のパタパタ表示（普通の順位表にする）
4. 振り返りの画面
5. 2 台の同期（1 台でプレイし、事前に録ったメンバーの回答と並べる見せ方に切り替える）

- 最後まで残すもの: 3D 表示、録音、採点（Azure と Claude）、結果発表、みんなの描写。
- 本番の備え: 採点の API が止まったときに固定の点数を返すモードと、事前に録画したデモ動画を用意する。

## リスク（推測を含む）

- 同時に話すと、隣の人の声がマイクに入って文字起こしが混ざるおそれがある（推測）。早めに 2〜3 人で同時に話して試す。
- 同時でも隣の発話が聞こえれば、バイアスは少し残る（推測）。
- スマホのマイクは会場の雑音を拾いやすく、発音評価の精度が下がるおそれがある（推測）。
- ネイティブアプリなので、遊べるのはアプリを入れた iPhone だけになる。Android の人は遊べない。
- 本番で同時に遊べる人数は、手元にある iPhone の台数が上限になる。
- Hack Day の開発時間は約 14 時間しかない。SwiftUI のアプリ、TypeScript のバックエンド、ルームの同期、ルーム画面、採点（文字起こし・発音評価・LLM）、3D 表示を全部そろえるには足りないおそれが大きい。
- 発表は Google Meet での画面共有と録画なので、iPhone の画面は Mac に映して共有する必要がある（推測）。

## Open Questions（決定木の状態）

- 作業分担: 各自が AI を使って作業するので、得意分野に合わせた細かい分担にはこだわらない（2026-10-21）。外せない制約は 1 つで、SwiftUI のアプリをビルドして iPhone に入れるには Mac が要り、Mac を持つのはチーム 5 人のうち 3 人（@TEIKOTA・@kameiryohei・@alfeeshahrin9-sudo）。
  - 最初の分担（2026-10-24）: バックエンドは @kameiryohei・@nozaworld、フロントエンド（SwiftUI のアプリ）は @TEIKOTA・@alfeeshahrin9-sudo・@takuma098。
  - フロントエンドは、各自が担当の画面を設計し、UI・UX を互いにレビューする。画面の設計は SwiftUI で行う必要はなく、Mac の無いメンバー（Windows）は HTML で画面の案を作って認識をすり合わせる。
- 確認したいこと（推測で置いている前提）:
  - Azure for Students のサブスクリプションで、Speech の有料プラン（S0）を作れるか。無料プラン（F0）は同時 1 セッションまでで、2 台の同時プレイに使えない。
  - Claude のクレジットが Claude API（Console）で使えるものか。claude.ai の利用プランの分だと API には使えない。
- 画面の流れを決めるときに決める:
  - 結果発表のタイミング（全員そろってから一斉に出すか、出来た人から出すか）と、採点が遅れた・失敗した人の扱い
    - 2026-11-11 に決定: 全員そろったら一斉に出す。ホストが締め切る操作は無くし、部屋が時間で締め切る。録音が終わるはずの時刻（開始 ＋ 回転 3 秒 ＋ 録音 20 秒）から、音声を 15 秒・採点を 30 秒まで待ち、間に合わなかった人は「採点できませんでした」にする（[ADR](../adr/20261111-score-only-with-checklist-and-drop-handmade-scenes.md)、仕組みは [`architecture.md`](./architecture.md)）
  - スマホでの録音の操作（一斉に自動で始めるか、早く話し終えた人が止められるか）
  - 採点の項目（何を何点で見るか）
- 外部 API（Azure の発音評価と Claude）は、すべてバックエンドが呼ぶ（2026-10-21 に決定）。iPhone は録音した音声（20 秒で約 0.6 MB）をバックエンドに送るだけにする。キーも Azure 用の一時トークンも iPhone に渡さず、回数の上限や止めるスイッチをバックエンド 1 か所で効かせるため。全員の採点がそろったかもバックエンドが判断する（ThatsFight の「出題と採点を単一 Node サーバーに集約」と同じ考え方）。コスト破産への備えは [`cost-safety.md`](./cost-safety.md)。
- バックエンドは Cloudflare Workers ＋ Durable Objects で動かす（2026-10-21 に決定）。部屋ごとの状態と WebSocket は Durable Objects に持たせる。回数の上限や DDoS の防御を Cloudflare に寄せられ、常に立てておくサーバーが要らないため。ThatsFight の Node のサーバーのコードは、そのままは使えず書き直す。構成は [`architecture.md`](./architecture.md)。
  - Azure は REST（短い音声用）で呼ぶ。Workers では Speech SDK が動く保証が無いため。REST の文書では発音評価の正解文が「必須」なので、最初に空の正解文で通るかを実際のキーで試し、通らなければ「文字起こし → その文を正解文にして発音評価」の 2 段にする。2 段になると、Azure の音声の時間が 2 回分（1 ラウンド約 0.03 USD）になり、待ち時間も少し延びる。
  - 空の正解文で REST が通ることを確かめた（2026-10-24）。TTS の 7 秒の音声で、文字起こしと Accuracy・Fluency・Prosody が返った。1 段のまま進める。
- 採点は 3 項目にし、合計で順位を決める（2026-10-21 に決定）。アプリが WAV を送る API は変えない。
  - **2026-11-10 の決定（英検の二次試験の評価の観点に沿わせる）。** 2026-11-11 に、バックエンドの採点をこの 1 通りに切り替えた（まとめ用の branch。main に入るのは、アプリと通しで動いたとき）。下の 2026-10-25 の採点と、手作りの 6 場面の要素の加点式は消した（[ADR](../adr/20261110-align-scoring-with-eiken-speaking-viewpoints.md)、[ADR](../adr/20261111-score-only-with-checklist-and-drop-handmade-scenes.md)）。
    - 軸と英検の観点: 内容＝応答内容・情報量、表現＝語い・文法・語法、話し方＝発音。意欲や態度は録音では測れないので対象外と明記する。重みは 50・25・25 のまま。
    - 名乗るのは「英検の二次試験の評価の観点に沿った採点」まで。「英検準拠」「英検の点数」とは言わない。
    - 内容 = 100 × 2PR/(P+R)（F1）。R は場面ごとのチェックリストの達成率（中心 2・理由 2・細部 1・その他 0.5 の重み）、P は言った描写のうち場面と合う割合。場面と矛盾する描写・場面に無い物・関係の無い話を間違いと数え、理由や推測・つなぎの言葉は数えない（[ADR](../adr/20261110-score-content-with-checklist-f1.md)）。
    - 級ごとの項目の数: `eiken-3` 中心 2・細部 1 ／ `eiken-pre2` 中心 3・理由 1・細部 2 ／ `eiken-2` 中心 4・理由 2（うち 1 つはつながり）・細部 2。どれも、その他は 2 件まで。満点の重みは項目だけで、`eiken-3` 5・`eiken-pre2` 10・`eiken-2` 14（2026-11-11 に、その他を満点に含めない形に改めた。[ADR](../adr/20261111-count-other-claims-as-bonus-and-require-actions-for-items.md)）。
    - チェックリストと見本の答えは、場面を作るときに Claude が作り、どの部品のことかをコードで照らして確かめ、場面の JSON に保存する。採点のたびには作らない。作り置きの JSON には生成で書いた関係も残す（[ADR](../adr/20261110-make-checklist-at-scene-generation.md)）。
    - 表現の段階は、IELTS から級ごとの文法と語彙の範囲（CEFR-J）に変える。
    - 録音の前に、級ごとの短い問いのお題を出す（`eiken-3`「誰が何をしている？」、`eiken-pre2`「…なぜ？」、`eiken-2` は理由の先までつなげることを促す。2級の文面は画面の PR で決める）。
    - 安定の条件: 同じ場面では毎回同じ項目。同じ答えを 5 回採点して内容の点の幅が 5 点以内（測定のスクリプト `measure-scoring-baseline.ts`。採点の実装の PR で `backend/scripts/` に入れる）。
    - 重みと項目の数は仮の値。30 場面を作り直した後、遊んだ答えで見直す。
    - 採点のときに Claude が返す形（2026-11-11 に決定）:
      - 判定として返すのは描写の一覧（`claims`）1 つだけ。各描写は `quote`（発話からの引用）・`verdict`（`correct` 合う・`contradiction` 矛盾・`absent` 場面に無い物・`offtopic` 無関係・`ignored` 数えない理由や推測やつなぎの言葉）・`item`（当たったチェックリストの `id`、無ければ null）・`level`（`full` 言えた・`partial` 一部）・`note`（間違いの理由、日本語）。項目の判定を別に返させない（同じ発話を 2 回判定して食い違うのを避ける）。
      - コードがこの一覧から作る: 項目ごとの達成（その項目に当たった描写の最も高い `level`。無ければ言えていない）、その他（`correct` で `item` が null のもの、2 件まで）、P = `correct` ÷（`correct` ＋ `contradiction` ＋ `absent` ＋ `offtopic`）、R、F1。
      - その他はおまけにする（2026-11-11 に決定。[ADR](../adr/20261111-count-other-claims-as-bonus-and-require-actions-for-items.md)）。満点の重みは checklist の項目だけ。その他は 1 件 0.5・2 件までを言えた重みに足し、言えた重みは満点で頭打ちにする（R は 1 を超えない）。見本どおりに言えば 100 点になる。内訳の「言えた」の分子・分母も、この数え方で出す。
      - 人や物の名前だけの描写は、中心・理由・つながりの項目に当てない（同じ ADR）。これらは、動作や関係（何をしているか・なぜか）を言ったときだけ一部以上にする。名前だけの描写は `item` を null にし、場面にあれば `correct`（その他の候補）。細部は、`accept` が物があることだけを求めるなら名前だけで当ててよい。
      - 描写の分け方: 動作と位置（前置詞の句）は別の描写にする。位置だけが誤りなら、動作の描写は `correct` で項目に当て、位置の描写だけを `contradiction` にする。1 つの文が 2 つの項目（動作と理由、動作とつながり）に当たるときは、項目ごとに描写を分け、引用は重なってよい。それぞれを 1 つの事実と数える（P にも 1 つずつ）。同じ場所・同じ `verdict`・同じ `item` の描写が 2 つ返ったら、コードが 1 つにまとめる。
      - `accept` に " / " で区切った別の言い方があるときは、どれか 1 つに当たれば言えたとする。
      - 引用は、大文字小文字・句読点・空白の違いを無視して文字起こしの中を探す。無ければその描写を捨てる（正しい描写にも間違いにも数えない）。当たっていた項目は、その分だけ下がる。
      - 表現の点は 0〜100 の 6 段階のまま、中身を級の目標にする（例: 80 は級の文法の一覧を正しく使えている、100 はそれに加えて一つ上の級の形も自然に使えている）。文法の一覧は生成と同じ定数（`GRADES`）から、その級までの分（下の級の文法も含む）を入れる。表現は発話の全部の英語（推測や、場面と合わない文も含む）で見て、描写の正誤は表現の点に入れない。0 は英語の語が無いときだけ（2026-11-11 の実測で、正しい英文の表現が 0 点になる回があったため、指示に書いた）。
      - 表現の点の前に、根拠（`expressionBasis`。どの形を正しく使えたか・どこが誤りかを英語で 1 文）を書かせる。返す欄の順は `claims` → `expressionBasis` → `expression` → `nextStep` → `rewrite`（2026-11-11 に `strength` を外した）。段階の文を直しても、同じ答えで 0・80・0・85・0 のように 0 点が返った（150 回中 6 回、2026-11-11 の測り直し）。点を根拠なしに書かせているためと見て、根拠を先に書かせる。根拠は結果の講評（`feedback.expressionBasis`）に入れてアプリへ送る（2026-11-12 に決定。それまでは送らなかった）。振り返りの画面には出さず、端末の記録（[`play-record.md`](./play-record.md)）に残し、苦手の分析に使う。根拠が無いとき（3 語未満で Claude を呼ばなかった回、2 回呼び直しても根拠が空だった回、固定の点数のモード）は null にする。空の文字列や、本物に見える固定の文は送らない（苦手の分析の入力に混ざらないように）。手元専用の採点の口（`POST /score`）も同じ根拠を返す。欄を足したので、足す前のビルドのアプリは結果を読めなくなる（`additionalProperties: false`。受け入れて、発表に使う端末は入れ直す）。
      - それでも 3 語以上の発話に、表現 0 点か空の根拠（空白だけも含む）が返ったら、同じ入力で 2 回まで呼び直す（計 3 回まで）。3 回目の実測（2026-11-11）で、0 点の回は根拠も空文字で、Claude が描写を書いたあと残りの欄を空の値で埋めて終えていたため。完全な応答（根拠があり、0 点でない）が得られたら、その応答の全部（描写・講評も）を使う。得られなければ、根拠が空でない応答を優先し、同じなら先の応答を使う。呼び直しが失敗したら、そこでやめる。呼び直した回数（0〜2）は結果に残す（その分 Claude を余計に呼ぶので、時間と費用も増える）。schema の `minLength` は使わない（SDK が文字列の制約として通すのは `format` だけ）。
      - 理由とつながりの `accept` は、行動と原因の文全体で書く（例: "a boy is running because it is raining"。生成の側の決まり）。中心・理由・つながりの主語は名詞にする。理由は、その行動に場面と矛盾しない理由を付けて言えば言えた（`accept` と違う理由でもよい）。行動だけなら理由には当てず、中心に当てる。
      - チェックリストの項目は 1 つにつき事実 1 つにする。中心の `accept` は「誰が何をしているか」だけにし、場所は、場所を問う細部の項目にだけ書く（生成の側の決まり。試験用の 3 場面もこれに合わせた）。判定の決まり: 中心は、その人や動物について `accept` の動作を言えば言えた（場所が無くてもよい）、誰が・何を（目的語）が違うか抜けていれば一部、名前だけなら当てない。細部は、`accept` の事実を言えば言えた、物があることだけを文で言えば一部、位置や様子を問う細部に名前だけなら当てない。位置だけの描写は、位置を問う細部があればそこに当て、無ければその他の候補にする（中心には当てない）。段階の文は Claude Code が下書きし、PR で確かめる。
      - 次に伸ばす一つ: 内容と表現のどちらを勧めるかは Claude が選ぶ。話し方にするかは、Azure の点からコードが決める（下の 2026-11-14 の変更）。内容のときは、言えていない項目の `id` も返す。コードは、その項目が本当に言えていないかを確かめ、だめなら重みの最も重い言えていない項目に差し替える。`gain` はコードが計算する。単位は合計の点の伸びで、「その項目を言えたときの合計 − 今の合計」を、合計を出すのと同じ式と重み（`SCORE_WEIGHTS`、既定 50・25・25）で出す（2026-11-11 に決定。今のアプリの「合計が何点伸びる」の意味のまま）。画面の足し算と合うよう、どちらの合計も画面に出すとおりに整数へ丸めてから引く。内容以外の次の一つと、項目が無いとき（全部言えた・短すぎる発話）は null。
      - 採点の Claude に渡すのは、級・`checklist`（`id`・`kind`・`label`・`accept`・`refs`）・関係つきの場面・`description`・文字起こし。話し方の 3 つの点は渡さない（2026-11-14 から。Azure と同時に呼ぶため）。重みと F1 の式は渡さない（点を意識した判定を避ける）。次の一つの項目は、`kind` の順（中心・理由を先に）で選ぶよう指示する。
      - アプリへ送るもの（`results` の `PlayerResult`。2026-11-11 に決定。[ADR](../adr/20261111-score-only-with-checklist-and-drop-handmade-scenes.md)）: `id`・`name`・`color`・`rank`・`score`・`transcript` は今までどおり。講評の一言（`comment`）は無くす。全員に同じ形を送り、他の人の内訳も載せる。採点できなかった人は `content` も `feedback` も null。
        - `content`（内容の内訳）: `claims`（描写の一覧。各描写は `quote`・`verdict`・`item`・`level`・`note`。引用は文字起こしに書かれているとおりの文字列で、話した順。数えない描写（`ignored`）は送らないので、`verdict` は `correct`・`contradiction`・`absent`・`offtopic`）、`items`（項目ごとの達成。`id`・`kind`・`label`・`level`（`full`・`partial`・`none`）。チェックリストの順）、`others`（その他として数えた件数）、`recall`（`earned`・`max`）、`precision`（`correct`・`said`）。割り算の結果は送らない（アプリが要れば計算する）。
        - `feedback`（講評）: `nextStep`（`kind`・`text`・`item`・`gain`）、`rewrite`（`before`・`after`・`reason`。無ければ null）、`speechTip`（`aspect`・`text`）。`expressionBasis`（表現の点の根拠。英語 1 文か null。2026-11-12 に足した。画面には出さない）。「良かった所」（`strength`）は無くす。採点の Claude にも書かせない。
        - アプリは、前の描写が終わった位置から先を、そのままの文字列で探して下線を引く。見つからなければ線を引かないだけで、点には関わらない（1 つの文が 2 つの項目に当たると、引用が重なる）。
      - 3 語未満の発話は Claude を呼ばず、内容・表現を 0 点にする（項目は全部「言えていない」、次の一つは「もう少し長く、文にして話してみよう。」で `item`・`gain` は null）。言い換え（`rewrite`）は、元の文が文字起こしにあるときだけ出す。話し方のコツ（`speechTip`）は、今までどおり Azure の点からコードが作る。失敗したときの扱い、モデル（Sonnet 5.5 の `low`）は変えない。
      - 計算の例（`eiken-pre2`、満点の重み 10）: 中心 3 つのうち 2 つを言えた（2＋2＋0）、理由が一部（2×0.5）、細部 2 つのうち 1 つ（1＋0）、その他 1 件（0.5）なら、R = 6.5 / 10 = 0.65。このとき正しい描写は 5 つ（項目に当たった 4 つ＋その他 1 つ）なので、場面に無い物を 1 つ言っていれば P = 5 / 6 ≈ 0.83、内容 = 100 × 2 × 0.65 × 0.83 ÷ (0.65 ＋ 0.83) ≈ 73 点。[ADR](../adr/20261110-score-content-with-checklist-f1.md) の Consequences の例（68 点）は、その他を満点に含めていたときの数え方（満点 11）で、正しい描写も 4 つと数え違えている（2026-11-11 に実装のテストで見つけた）。
  - 内容: 場面に合っているか、何を描写できたか。文字起こしと場面の配置の情報を Claude に渡し、採点基準の段階で 0〜100 を付ける（2026-10-25 に決定。[ADR](../adr/20261025-score-content-with-layout-and-rubric-bands.md)）。
    - 渡す場面の情報: 配置の JSON の部品ごとの名前・`words`・大きさ・座標・向き・動きと、座標の決まり（Y が上、カメラは +Z 側）。画像は渡さない。Claude の読み取りに時間がかかるため。
    - 位置の関係（上・下・横など）は、まず座標のまま渡して Claude に読ませる。場面 3〜5 個と、関係を含む発話で測り、位置の関係の判定を 2 割以上読み違えたら、次のどちらかに切り替える。
      - 生成で書いた関係（`on`・`next_to` など）を配置に残して渡す。
      - 座標から関係を計算して渡す。
    - 段階: 0・20・40・60・80・100 の 6 段階に説明を書き、間の点も付けてよい。段階には「言ったことが場面と合っているか（正確さ）」を含め、場面に無いことや間違いが多ければ段階が下がる。
    - 減点: 引き算の減点はしない。場面に無いことを言ったときは、上の段階の正確さで反映する。
    - 1 人につき Claude を 1 回呼ぶ。プロンプトには、採点基準（段階の説明）・場面の metadata（上）・場面の説明文（補足）・文字起こしを入れる。
    - 場面の説明文（`description`）は、作り置きのときに Claude が書き、人が画像と一緒に確かめたもの。対戦中に説明文や採点の一覧を作り直さない。
    - 要素（`elements`）は渡さない。言えていない主な物は、Claude が metadata の中から選ぶ（下の「次に伸ばす一つ」）。
    - 左右・前後は、どの向きから見たものでも正解にする。プレイヤーは場面を回せるため。
  - 表現: 語彙や文の組み立て。Claude が採点する。IELTS の語彙（Lexical Resource）と文法（Grammatical Range and Accuracy）の考え方で段階の説明を書き、0〜100 に直す（2026-10-25）。
  - 内容・表現の段階の説明の文は、Claude Code が下書きし、野沢さんが PR で確かめる。IELTS・英検の公式の文は丸写ししない。文そのものは別の PR で書く。
  - 手作りの 6 場面（公園・教室・駅前・雨のバス停・海辺・カフェ）は、遊べる場面から外した（2026-11-11。[ADR](../adr/20261111-score-only-with-checklist-and-drop-handmade-scenes.md)）。3D のファイル（`assets/scenes/`）は残す。2026-10-25 には、部品の配置で作り直して同じ形で採点するとしていたが、作り直さない。
  - 内容の採点の経緯:
    - 2026-10-24 には、要素ごとの加点式にしていた。人が場面を要素（例: 公園で 15 点、犬 15 点、犬がボールに向かって走っている 25 点）に分けて配点し、LLM が要素ごとに「満点・半分・なし」を返し、バックエンドが足す。一覧に無い正しい描写は上限付き（10 点）で足す。例文との一致度では採点しない（言い回しが違うだけで点が下がるため）。
    - 2026-10-25 に、上の段階の形に置き換えた。作った文の一覧と照らすのではなく、場面とプレイヤーの説明が合っているかを重く見るため。
    - 同じ日に、いったん「場面の画像（1 方向から描いた 1 枚）を Claude に渡す」で野沢さんと合意した。画像の読み取りが遅いので、配置の情報を渡す形に変えた。
  - 話し方: 流暢さ・発音・抑揚。Azure の発音評価の点数を使う。AccuracyScore・FluencyScore・ProsodyScore の平均にする（2026-10-24）。PronScore はこの 3 つをまとめた点なので、足すと二重に数える。
  - 振り返りには、各項目の点数と講評を出す（2026-10-24）。講評は「次に伸ばす一つ」「本人の一文の言い換え」「話し方のコツ」の 3 つにする（2026-11-11 に「できたこと」を外した。言えたことは、内容の内訳の項目と描写で見せる。[ADR](../adr/20261111-score-only-with-checklist-and-drop-handmade-scenes.md)）。2026-10-24 には「できたこと（本人の発話の引用つき）」を入れた 4 つにしていた。
    - 次に伸ばす一つは、Claude が選ぶ（2026-10-25）。内容・表現・話し方のどれを伸ばすかと、その一言（短い英語の例つき）を返させる。食い違わないよう、プロンプトに話し方の 3 つの点（Azure の正確さ・なめらかさ・抑揚）も入れる。Azure は Claude より先に呼んでいるので、点はそろっている。
      - 話し方のコツ（どの単語を直すか）は、今までどおりバックエンドが Azure の単語ごとの点から作る。
      - 2026-10-24 には、LLM に選ばせずバックエンドが決めていた。要素ごとの配点から「足すと合計点が最も伸びるもの」を計算でき、採点と講評の食い違いを避けられたため。新しい採点では要素の配点が無く、言えていない主な物を選ぶのはもともと Claude なので、選ぶところまで任せる。
      - 2026-10-24 の加点式では「言えなかった要素のうち、足すと合計点が最も伸びるもの」にしていた。新しい採点では要素に配点が無いので、この決め方は使えない。
    - 2026-11-14 に変更: 採点の待ちを縮めるため、端末の文字起こしがあれば Azure と Claude を同時に呼ぶ（staging の実測で、採点 1 回の中央値は Azure 4.0 秒・Claude 4.0 秒で、足し算の 7.8 秒かかっていた）。そのため Claude には話し方の点を渡さず、Claude は内容か表現を選ぶ。Azure の点が出たあと、話し方の 3 つの点の最小が「内容と表現の低いほう − 20」以下で、かつ 80 未満のときだけ、コードが次の一つを話し方に差し替える。文は話し方のコツ（`speechTip`）と同じにし、`item`・`gain` は null。端末の文字起こしが無いときは、今までどおり Azure の文字起こしを待ってから Claude を呼ぶ（次の一つの決め方は同じ）。
    - 引用と言い換え元は、文字起こしに含まれるものだけを出す。自動の文字起こしなので、認識の誤りらしい語は言い換えの対象にしない。
    - 話し方のコツは、Azure の 3 つの点のうち最も低いものから決まった文で作る。発音が最も低ければ、点の最も低い一語だけを名指しする（低い単語を全部示すと意欲が下がるため）。
    - みんなの描写には「できたこと」の一文だけを出す。
  - 重みは、最初は内容を重くする（内容 50%・表現 25%・話し方 25%）。今決めても意味の薄い値なので、実際に遊びながらチームで調整する（2026-10-21）。調整しやすいよう、重みはコードに埋め込まず設定値として持つ（推測）。2026-10-25 の採点の見直しでも重みは変えない。
- 話し方（流暢さ・発音・抑揚）の採点には Azure の発音評価を使う（2026-10-21 に決定）。費用・制限・返る値・応答時間は [`azure-pronunciation-assessment.md`](./azure-pronunciation-assessment.md)。応答時間は Hack Day の前に実測する。
- 文字起こし（2026-10-21 に決定）:
  - まず、Azure の発音評価の呼び出しで返る文字起こしをそのまま使う。1 回の呼び出しで文字起こしと話し方の点数がそろい、作り始めを軽くできる。
  - Hack Day の前の録音テストで文字起こしの誤りが目立ったら、精度の高い文字起こし AI（ElevenLabs Scribe v2、MAI-Transcribe-2 など）で先に文字にし、その文を正解文として Azure で評価する構成に切り替える。正解文なしの評価は通常の音声認識と別のモデルを使うため。
  - 切り替えると呼び出しが 2 段になり、作り直しと待ち時間の増加が出る。切り替えやすいよう、文字起こしの取得は差し替えられる作りにしておく（推測）。
  - 文字起こしの精度が悪いとの声があり、iPhone の端末の中での文字起こし（iOS 26 の SpeechAnalyzer）に切り替えた（2026-10-25）。録り終えた WAV を端末で文字にし、音声と一緒に送る（`X-Transcript` ヘッダー）。部屋はその文を Azure の正解文と Claude の採点に使う。費用は増えず、Azure の呼び出しも 1 回のまま。端末で文字にできなかった（非対応の端末・5 秒の時間切れ・失敗）ときは、これまでどおり Azure の文字起こしを使う。精度が下がったら戻す。
- 内容・表現の採点と講評には Claude を使う（2026-10-21 に決定）。
  - まず Claude Haiku 5.5（`claude-haiku-5-5`、effort `high`）で作り、質が足りなければ Claude Sonnet 5.5（`claude-sonnet-5-5`、effort `medium`）に上げる。
  - 本番の採点は Claude Sonnet 5.5（`claude-sonnet-5-5`）の effort `low` にした（2026-10-25、PR #50）。モデルと effort は環境変数 `CLAUDE_MODEL`・`CLAUDE_EFFORT` で変えられる。
  - 点数と講評は、JSON スキーマを指定する構造化出力（`output_config.format`）で受け取る。
  - Hack Day の前の録音テストで、次の基準で両方を比べる（推測）。
    - 同じ文字起こしを何度か採点させたときの点数のぶれ
    - チームの感覚との一致
    - 文字起こしを渡してから点数と講評が返るまでの時間
  - 料金（100 万トークンあたり、入力 / 出力）: Haiku 5.5 は 0.10 / 0.50 USD、Sonnet 5.5 は 2.00 / 10.00 USD（2026-10-06 時点）。1 人 1 回（入力約 2,000・出力約 500 トークンと仮定）で、Haiku は約 0.0005 USD、Sonnet は約 0.009 USD（思考の分を除く）。
  - 方針: 理想は、文字起こしではなく音声そのものを AI に渡し、イントネーション・抑揚などの音声の変化も採点に含めること。それが無理なら、最も精度の高い文字起こし AI を使う。特定のサービスにはこだわらない。
  - 比べた観点: 精度、返るもの（文字起こしだけか、抑揚などの評価も返るか）、費用、ライブ字幕に使えるか（遅延）、同時に何人まで使えるか。
  - ライブ字幕は出さないと決めた（2026-10-21、[`screen-flow.md`](./screen-flow.md)）。話し終えてから文字にする型の文字起こしで足り、ストリーミングへの対応は選定条件から外れる。
