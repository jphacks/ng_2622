## 作品名（仮、2026-10-24）

ScenEnglish（シーングリッシュ）。Scene と English を合わせた造語。読みを「シングリッシュ」にしないのは、シンガポールの英語（Singlish）と紛れるため。MTG で確定させる。

- 似た名前（2026-10-24 に Web 検索）: 「ScenEnglish」と完全に同じ名前のアプリは見つからなかった。近いものに、写真から英単語を出す英語学習アプリ「Scene English」（App Store）と、場面を作って会話を練習する「SceneLingo」がある。

## 目的

全員が同じ 3D シーンを**同時に**見て、各自の解釈で英語で描写し、その発話を AI が判定して競う。

## 動機（2026-10-24）

- 課題: 英語を「話す」機会が足りない。単語帳でどれだけ覚えても、実際に使う機会がない。既存の英会話アプリは決まった文（定型文）を練習するもので、面白みに欠けてモチベーションが続かない。友達と同時に遊ぶゲームにして、自分の言葉で話す量を増やす。
- 面白さ: 同じものを見ても、人によって見方と言い方が違う。その違いを比べる面白さを英語でやる（作品の核）。
- 学びの中身: 見たものを英語で説明する力（描写力）。試験や実際の会話で求められるのに、練習して点数で振り返れる場が少ない。

## 決まったこと

- 全員が同時にプレイする。順番には遊ばない。
  - 理由: 順番に遊ぶと、後の人は前の人の発話を聞いて真似でき（バイアス）、後の人ほど有利になる。
- 各プレイヤーは自分のスマホで遊ぶ。スマホに 3D モデルを表示し、それを見ながらスマホに向かって話す。結果もそのスマホに出る。
- ホログラムは作らず、各自の端末で 3D モデルを表示する形で固定する（2026-10-21）。できそうなら後でホログラムを足す。
  - 理由: 解像度などの見え方をチームで把握できておらず、うまくいくか分からない。ホログラム版を並行して作るのは手間の割に無駄になりやすい。
  - 足す場合は、真ん中に置いた iPad をホログラム表示専用にし、全員で見る共有画面（ルーム画面）もそのとき改めて検討する。
- 全員で見る共有画面（ルーム画面）は当面持たない（2026-10-21）。全員が同じプレイヤー画面を使う。
- 端末どうしをつなぐ「部屋」の仕組みは残す（2026-10-21）。1 人がアプリで部屋を作ってコード（または QR）を出し、他の人はそれで入る。シーンの選択とスタートは部屋を作った人が行う（作り置きの場面に入れ替えたあとは、難易度だけを選ぶ。[`scene-protocol.md`](./scene-protocol.md)）。結果の画面では、自分と相手の描写と点数を並べて見られる。画面の流れは [`screen-flow.md`](./screen-flow.md)。
- 技術スタック: フロントエンドは SwiftUI のネイティブアプリ、バックエンドは TypeScript の API（2026-10-21）。ADR: [`20261021-adopt-swiftui-app-and-cloudflare-workers-backend`](../adr/20261021-adopt-swiftui-app-and-cloudflare-workers-backend.md)。

| 画面 | 端末 | 役割 |
| --- | --- | --- |
| プレイヤー画面 | 各自の iPhone（SwiftUI アプリ） | 3D 表示、録音、結果 |
| ホログラム画面（できそうなら） | 真ん中の iPad | 3D のホログラム表示だけ |

- 本番で使う iPhone: 可能なら 2 台で 2 人が同時にプレイする。無理なら有料アカウントの持ち主の iPhone 1 台だけにする。「無理なら」は、2 台を同時に始める仕組みが間に合わない場合と解釈している（推測）。
- アプリの入れ方: 有料アカウント（個人の登録）の持ち主が、本番の iPhone に Xcode から直接入れる。
- Hack Day の MVP には、最初から 2 台の同時プレイを入れる（2026-10-21）。作品の核である「同時に解釈を比べる」を最初から見せるため。間に合わないときは、下の 1 台のときの見せ方で発表する。
- 基本は複数人で同時にプレイする方向で作る。1 台だけになったときは、1 人がその場でプレイし、結果の画面に事前に録っておいたチームメンバーの回答とその点数を並べて比べる。事前の録音は各自が別々に録るので、真似の問題は起きない。

## 遅れたときに削る順番（2026-10-21 に決定）

演出や便利な機能から削り、同時プレイは最後に削る。作品の核（同じ場面を見て描写し、比べる）を最後まで守るため。

1. QR の読み取り（部屋のコード入力だけにする）
2. シーンのサムネイル（名前の一覧だけにする）
3. 結果発表のパタパタ表示（普通の順位表にする）
4. 振り返りの画面
5. 2 台の同期（1 台でプレイし、事前に録ったメンバーの回答と並べる見せ方に切り替える）

- 最後まで残すもの: 3D 表示、録音、採点（Azure と Claude）、結果発表、みんなの描写。
- 本番の備え: 採点の API が止まったときに固定の点数を返すモードと、事前に録画したデモ動画を用意する。

## リスク（推測を含む）

- 同時に話すと、隣の人の声がマイクに入って文字起こしが混ざるおそれがある（推測）。早めに 2〜3 人で同時に話して試す。
- 同時でも隣の発話が聞こえれば、バイアスは少し残る（推測）。
- スマホのマイクは会場の雑音を拾いやすく、発音評価の精度が下がるおそれがある（推測）。
- ネイティブアプリなので、遊べるのはアプリを入れた iPhone だけになる。Android の人は遊べない。
- 本番で同時に遊べる人数は、手元にある iPhone の台数が上限になる。
- Hack Day の開発時間は約 14 時間しかない。SwiftUI のアプリ、TypeScript のバックエンド、ルームの同期、ルーム画面、採点（文字起こし・発音評価・LLM）、3D 表示を全部そろえるには足りないおそれが大きい。
- 発表は Google Meet での画面共有と録画なので、iPhone の画面は Mac に映して共有する必要がある（推測）。

## Open Questions（決定木の状態）

- 作業分担: 各自が AI を使って作業するので、得意分野に合わせた細かい分担にはこだわらない（2026-10-21）。外せない制約は 1 つで、SwiftUI のアプリをビルドして iPhone に入れるには Mac が要り、Mac を持つのはチーム 5 人のうち 3 人（@TEIKOTA・@kameiryohei・@alfeeshahrin9-sudo）。
  - 最初の分担（2026-10-24）: バックエンドは @kameiryohei・@nozaworld、フロントエンド（SwiftUI のアプリ）は @TEIKOTA・@alfeeshahrin9-sudo・@takuma098。
  - フロントエンドは、各自が担当の画面を設計し、UI・UX を互いにレビューする。画面の設計は SwiftUI で行う必要はなく、Mac の無いメンバー（Windows）は HTML で画面の案を作って認識をすり合わせる。
- 確認したいこと（推測で置いている前提）:
  - Azure for Students のサブスクリプションで、Speech の有料プラン（S0）を作れるか。無料プラン（F0）は同時 1 セッションまでで、2 台の同時プレイに使えない。
  - Claude のクレジットが Claude API（Console）で使えるものか。claude.ai の利用プランの分だと API には使えない。
- 画面の流れを決めるときに決める:
  - 結果発表のタイミング（全員そろってから一斉に出すか、出来た人から出すか）と、採点が遅れた・失敗した人の扱い
  - スマホでの録音の操作（一斉に自動で始めるか、早く話し終えた人が止められるか）
  - 採点の項目（何を何点で見るか）
- 外部 API（Azure の発音評価と Claude）は、すべてバックエンドが呼ぶ（2026-10-21 に決定）。iPhone は録音した音声（20 秒で約 0.6 MB）をバックエンドに送るだけにする。キーも Azure 用の一時トークンも iPhone に渡さず、回数の上限や止めるスイッチをバックエンド 1 か所で効かせるため。全員の採点がそろったかもバックエンドが判断する（ThatsFight の「出題と採点を単一 Node サーバーに集約」と同じ考え方）。コスト破産への備えは [`cost-safety.md`](./cost-safety.md)。
- バックエンドは Cloudflare Workers ＋ Durable Objects で動かす（2026-10-21 に決定）。部屋ごとの状態と WebSocket は Durable Objects に持たせる。回数の上限や DDoS の防御を Cloudflare に寄せられ、常に立てておくサーバーが要らないため。ThatsFight の Node のサーバーのコードは、そのままは使えず書き直す。構成は [`architecture.md`](./architecture.md)。
  - Azure は REST（短い音声用）で呼ぶ。Workers では Speech SDK が動く保証が無いため。REST の文書では発音評価の正解文が「必須」なので、最初に空の正解文で通るかを実際のキーで試し、通らなければ「文字起こし → その文を正解文にして発音評価」の 2 段にする。2 段になると、Azure の音声の時間が 2 回分（1 ラウンド約 0.03 USD）になり、待ち時間も少し延びる。
  - 空の正解文で REST が通ることを確かめた（2026-10-24）。TTS の 7 秒の音声で、文字起こしと Accuracy・Fluency・Prosody が返った。1 段のまま進める。
- 採点は 3 項目にし、合計で順位を決める（2026-10-21 に決定）。アプリが WAV を送る API は変えない。
  - 内容: 場面に合っているか、何を描写できたか。文字起こしと場面の配置の情報を Claude に渡し、採点基準の段階で 0〜100 を付ける（2026-10-25 に決定。[ADR](../adr/20261025-score-content-with-layout-and-rubric-bands.md)）。
    - 渡す場面の情報: 配置の JSON の部品ごとの名前・`words`・大きさ・座標・向き・動きと、座標の決まり（Y が上、カメラは +Z 側）。画像は渡さない。Claude の読み取りに時間がかかるため。
    - 位置の関係（上・下・横など）は、まず座標のまま渡して Claude に読ませる。場面 3〜5 個と、関係を含む発話で測り、位置の関係の判定を 2 割以上読み違えたら、次のどちらかに切り替える。
      - 生成で書いた関係（`on`・`next_to` など）を配置に残して渡す。
      - 座標から関係を計算して渡す。
    - 段階: 0・20・40・60・80・100 の 6 段階に説明を書き、間の点も付けてよい。段階には「言ったことが場面と合っているか（正確さ）」を含め、場面に無いことや間違いが多ければ段階が下がる。
    - 減点: 引き算の減点はしない。場面に無いことを言ったときは、上の段階の正確さで反映する。
    - 1 人につき Claude を 1 回呼ぶ。プロンプトには、採点基準（段階の説明）・場面の metadata（上）・場面の説明文（補足）・文字起こしを入れる。
    - 場面の説明文（`description`）は、作り置きのときに Claude が書き、人が画像と一緒に確かめたもの。対戦中に説明文や採点の一覧を作り直さない。
    - 要素（`elements`）は渡さない。言えていない主な物は、Claude が metadata の中から選んで返す（「次に伸ばす一つ」に使う）。
    - 左右・前後は、どの向きから見たものでも正解にする。プレイヤーは場面を回せるため。
  - 表現: 語彙や文の組み立て。Claude が採点する。IELTS の語彙（Lexical Resource）と文法（Grammatical Range and Accuracy）の考え方で段階の説明を書き、0〜100 に直す（2026-10-25）。
  - 内容・表現の段階の説明の文は、Claude Code が下書きし、野沢さんが PR で確かめる。IELTS・英検の公式の文は丸写ししない。文そのものは別の PR で書く。
  - 手作りの 6 場面（公園・教室・駅前・雨のバス停・海辺・カフェ）も部品の配置で作り直し、同じ形で採点する（2026-10-25）。作り直すまで 6 場面は使わない。外すのは、作り置きの場面（[`scene-protocol.md`](./scene-protocol.md)）と新しい採点が本番に入るのと同時にする。それまでは今の採点で遊べるようにしておく。
  - 内容の採点の経緯:
    - 2026-10-24 には、要素ごとの加点式にしていた。人が場面を要素（例: 公園で 15 点、犬 15 点、犬がボールに向かって走っている 25 点）に分けて配点し、LLM が要素ごとに「満点・半分・なし」を返し、バックエンドが足す。一覧に無い正しい描写は上限付き（10 点）で足す。例文との一致度では採点しない（言い回しが違うだけで点が下がるため）。
    - 2026-10-25 に、上の段階の形に置き換えた。作った文の一覧と照らすのではなく、場面とプレイヤーの説明が合っているかを重く見るため。
    - 同じ日に、いったん「場面の画像（1 方向から描いた 1 枚）を Claude に渡す」で野沢さんと合意した。画像の読み取りが遅いので、配置の情報を渡す形に変えた。
  - 話し方: 流暢さ・発音・抑揚。Azure の発音評価の点数を使う。AccuracyScore・FluencyScore・ProsodyScore の平均にする（2026-10-24）。PronScore はこの 3 つをまとめた点なので、足すと二重に数える。
  - 振り返りには、各項目の点数と講評を出す（2026-10-24）。講評は「できたこと（本人の発話の引用つき）」「次に伸ばす一つ」「本人の一文の言い換え」「話し方のコツ」の 4 つにする。
    - 次に伸ばす一つは LLM に選ばせず、バックエンドが決める。採点と講評が食い違わないようにするため。新しい採点では、Claude が返した「言えていない主な物」の先頭を選ぶ。言えていない物が無ければ、表現と話し方の低い方。LLM はヒントの文だけを書く。
      - 2026-10-24 の加点式では「言えなかった要素のうち、足すと合計点が最も伸びるもの」にしていた。新しい採点では要素に配点が無いので、この決め方は使えない。
    - 引用と言い換え元は、文字起こしに含まれるものだけを出す。自動の文字起こしなので、認識の誤りらしい語は言い換えの対象にしない。
    - 話し方のコツは、Azure の 3 つの点のうち最も低いものから決まった文で作る。発音が最も低ければ、点の最も低い一語だけを名指しする（低い単語を全部示すと意欲が下がるため）。
    - みんなの描写には「できたこと」の一文だけを出す。
  - 重みは、最初は内容を重くする（内容 50%・表現 25%・話し方 25%）。今決めても意味の薄い値なので、実際に遊びながらチームで調整する（2026-10-21）。調整しやすいよう、重みはコードに埋め込まず設定値として持つ（推測）。2026-10-25 の採点の見直しでも重みは変えない。
- 話し方（流暢さ・発音・抑揚）の採点には Azure の発音評価を使う（2026-10-21 に決定）。費用・制限・返る値・応答時間は [`azure-pronunciation-assessment.md`](./azure-pronunciation-assessment.md)。応答時間は Hack Day の前に実測する。
- 文字起こし（2026-10-21 に決定）:
  - まず、Azure の発音評価の呼び出しで返る文字起こしをそのまま使う。1 回の呼び出しで文字起こしと話し方の点数がそろい、作り始めを軽くできる。
  - Hack Day の前の録音テストで文字起こしの誤りが目立ったら、精度の高い文字起こし AI（ElevenLabs Scribe v2、MAI-Transcribe-2 など）で先に文字にし、その文を正解文として Azure で評価する構成に切り替える。正解文なしの評価は通常の音声認識と別のモデルを使うため。
  - 切り替えると呼び出しが 2 段になり、作り直しと待ち時間の増加が出る。切り替えやすいよう、文字起こしの取得は差し替えられる作りにしておく（推測）。
- 内容・表現の採点と講評には Claude を使う（2026-10-21 に決定）。
  - まず Claude Haiku 5.5（`claude-haiku-5-5`、effort `high`）で作り、質が足りなければ Claude Sonnet 5.5（`claude-sonnet-5-5`、effort `medium`）に上げる。
  - 本番の採点は Claude Sonnet 5.5（`claude-sonnet-5-5`）の effort `low` にした（2026-10-25、PR #50）。モデルと effort は環境変数 `CLAUDE_MODEL`・`CLAUDE_EFFORT` で変えられる。
  - 点数と講評は、JSON スキーマを指定する構造化出力（`output_config.format`）で受け取る。
  - Hack Day の前の録音テストで、次の基準で両方を比べる（推測）。
    - 同じ文字起こしを何度か採点させたときの点数のぶれ
    - チームの感覚との一致
    - 文字起こしを渡してから点数と講評が返るまでの時間
  - 料金（100 万トークンあたり、入力 / 出力）: Haiku 5.5 は 0.10 / 0.50 USD、Sonnet 5.5 は 2.00 / 10.00 USD（2026-10-06 時点）。1 人 1 回（入力約 2,000・出力約 500 トークンと仮定）で、Haiku は約 0.0005 USD、Sonnet は約 0.009 USD（思考の分を除く）。
  - 方針: 理想は、文字起こしではなく音声そのものを AI に渡し、イントネーション・抑揚などの音声の変化も採点に含めること。それが無理なら、最も精度の高い文字起こし AI を使う。特定のサービスにはこだわらない。
  - 比べた観点: 精度、返るもの（文字起こしだけか、抑揚などの評価も返るか）、費用、ライブ字幕に使えるか（遅延）、同時に何人まで使えるか。
  - ライブ字幕は出さないと決めた（2026-10-21、[`screen-flow.md`](./screen-flow.md)）。話し終えてから文字にする型の文字起こしで足り、ストリーミングへの対応は選定条件から外れる。
- アプリの入れ方の残り（non-blocker）: 開発中に、各メンバーが自分の iPhone へどう入れるか。アカウントは個人（Individual）の登録なので、他のメンバーは署名に要る証明書・プロファイルを扱えない（Apple 公式ヘルプ）。手段の候補は 3 つ。
  - 各自の無料 Apple ID で入れる（7 日で期限が切れる）
  - アカウントの持ち主がまとめて入れる
  - TestFlight の内部テストで配る（App Store Connect のユーザーとして招待、最大 100 人、ビルドは 90 日で期限が切れる）
