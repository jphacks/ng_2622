# 2026/10/25 AI の場面は遊ぶ前に作り置き、待合では難易度だけを選ぶ

## Status
- accepted

## Situation
- Hack Day の 2 日目。Code Freeze は 10/25 15:00。
- 2026-10-24 に、場面は作り置いた部品を配置の JSON で並べて作ると決めた（[20261024-compose-scenes-from-stored-parts](./20261024-compose-scenes-from-stored-parts.md)）。AI の場面は、待合でホストが一言（お題）を書き、`POST /scenes/generate` でその場で作って R2 に保存する予定だった（[`docs/design/scene-protocol.md`](../design/scene-protocol.md)）。
- `POST /scenes` と R2 はまだ入れていない。採点の場面の情報（`backend/src/scoring/scenes.json`）は、repo の JSON を Worker に同梱している。
- 遊べる場面は手作りの 6 つ（公園・教室・駅前・雨のバス停・海辺・カフェ）だけ。

## Context
- ホストが一言を書いて作らせると、書いた人だけが場面の中身を知っていて有利になる。全員が同じ条件で描写して比べる、という作品の核に合わない。
- その場で作ると、待合で待たせる（実測で 3〜14 秒）。崩れた場面や言いにくい場面を、遊ぶ前に人が確かめられない。
- 一言を自由に書けると、不適切な一言への対策や、1 回の生成の費用の上限も要る。

## Material for decision
- grill の決定（2026-10-25）: 作り置き、難易度ごとに 10 場面、PNG で目で確かめる、repo に同梱、生成の口は合言葉付きで保存しない、待合では難易度だけ、まだ出ていない場面からランダム。
- 実測（2026-10-25、Haiku 5.5、手元の `wrangler dev`、一言を渡す旧形式の口）: かんたん 3〜5 秒、ふつう 3〜8 秒、むずかしい 12〜14 秒。
- `scripts/scene/render_layout.py`（配置の JSON を PNG に描く）。
- 比べた案:

| 案 | 中身 | 良い点 | だめな点 |
| --- | --- | --- | --- |
| ホストの一言でその場で作る（2026-10-24 の決定） | 待合でホストがお題を書き、その場で生成して R2 に保存 | 毎回新しい場面。好きな場面を頼める | 書いた人が有利。待たせる。人が確かめられない。不適切な一言と費用の対策が要る |
| 待合でその場で作る（お題なし） | ホストは難易度だけ選び、その場でテーマも Claude に選ばせる | 中身を誰も知らない。毎回新しい | 待たせる。人が確かめられず、崩れた場面がそのまま出る。本番で Claude が止まると遊べない |
| 作り置き＋ R2 | 手元で作り、確かめたものを `POST /scenes` で R2 に保存 | 後から足すのに deploy が要らない | `POST /scenes` と R2 をまだ入れていない。場面の中身を PR で見られない |
| 作り置き＋ repo（採用） | 手元で作り、確かめたものを repo の JSON にして Worker に同梱 | 待たない。人が確かめたものだけが出る。PR で見られ、git に履歴が残る。採点の `scenes.json` と同じ扱いで、新しい仕組みが要らない | 場面を足すたびに deploy が要る。数は作り置いた分だけ |
| 作り置き＋ Supabase | 確かめた場面を Supabase の表に入れる | 後から足すのに deploy が要らない | 新しいサービスの準備（プロジェクト・キー・PR ごとのプレビューの設定）が要る。30 場面の決まったデータに DB は要らない |

## Decision
- AI の場面は、遊ぶ前にスクリプトでまとめて作り置く。まず難易度ごとに 10 場面（計 30）。`render_layout.py` で PNG に描き、人が目で確かめたものだけを repo の JSON にして Worker に同梱する。置き場所（`backend/src/scenes/pool/` の案）と ID（`gen-` ＋ 10 文字の案）は作るときに決める。
- 作り置きのスクリプトも `POST /scenes/generate` を呼ぶ。Claude への指示と座標の計算を 1 箇所にまとめるため。呼ぶ先は手元の `wrangler dev` で、生成に使う Claude のキーは手元の `.dev.vars` だけに置く。本番では作り置きをしない。
- `POST /scenes/generate` は合言葉（`SCENE_WRITE_TOKEN`）が要り、アプリは呼ばない。入力は `{ difficulty, theme? }` で、`theme` を省けば Claude が指示の中のテーマの一覧から選ぶ。配置の JSON を返すだけで保存しない。クラウドに残すときは、その JSON を `POST /scenes` に送る（`POST /scenes` と R2 は、亀井さんのエージェントが使うときに入れる）。
- Claude は 1 回の呼び出しで、正解の文（要素）を先に、その文を描ける部品と関係を後に書く。
- 待合では、ホストは難易度だけを選ぶ。場面は、その部屋でまだ出ていないものからランダムに出し、全部出たら最初に戻る。名前もスタートまで見せない。
- ホストの一言の入力、不適切な一言への対策、待合での 20 秒の締め切り、1 回の生成の費用の上限は外す。作り置きにして、合言葉と手元での実行に限ったため。
- Supabase は採らない。作り置きの場面は決まったデータで、repo の JSON で足り、新しいサービスの準備が要らないため。

## Consequences
- 良い面: 誰も中身を知らない場面で、全員が同じ条件で遊べる。待合で待たない。人が確かめた場面だけが出る。本番で場面を作るための Claude の呼び出しが無くなる。
- 良い面: 場面が PR で見られ、git に履歴が残る。採点の場面の情報と同じく Worker に同梱するので、新しい保存先が要らない。
- トレードオフ: 遊べる場面の数は、作り置いた分（まず 30）だけ。同じ顔ぶれで何度も遊ぶと、いずれ同じ場面が出る。場面を足すたびに deploy が要る。
- トレードオフ: 好きな場面を頼んで遊ぶ楽しさは無くなる。
- 待合の画面と `start` のメッセージを、シーンの一覧から難易度の選択に変える必要がある。手作りの 6 場面は部品の配置で作り直し、作り置きの場面と新しい採点（[20261025-score-content-with-layout-and-rubric-bands](./20261025-score-content-with-layout-and-rubric-bands.md)）が本番に入るのと同時に外す。
- 難易度の中身（かんたん＝初級の動詞で要素 4、ふつう＝中級で 6、むずかしい＝上級で 8）は推測の案で、作って遊んでから直す。
