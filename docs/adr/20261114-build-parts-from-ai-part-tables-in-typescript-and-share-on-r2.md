# 2026/11/14 部品は AI が部品表を書き TS で組み、ID の規約で引き、R2 に置いてみんなで使う

## Status
- accepted
- これは、2026-10-21 の決定（[`docs/design/scene-generation.md`](../design/scene-generation.md) の「C で部品を作り、A で並べる」）を部分的に改める。改めるのは、部品をサーバーの Blender で AI が書いたスクリプトから作る所。2026-10-21 の決定は ADR ではなく設計の文書にあるので、そちらに注を書いた。
- これは、[20261110-write-grade-sentences-before-scene-parts](./20261110-write-grade-sentences-before-scene-parts.md) の「2 回目に渡す部品は、今は全部」を、苦手の場面の生成に限って部分 supersede する（その ADR の Status に書いた）。

## Situation
- Award Day（2026-11-15）の前日の夜中。2026-11-14 の 1 時に、リーダーが「苦手の場面と、部品をその場で作ることを、Award Day に間に合わせる」と決めた。アプリの変更は TestFlight 1.0.1 (5) の締め切り（11/14 12:00）に縛られる。サーバーは当日の朝まで PR で直せる。
- 苦手の分析はある（[20261113-analyze-weak-points-with-ai-from-on-device-counts](./20261113-analyze-weak-points-with-ai-from-on-device-counts.md)）。ただ、「次はここ」を押した先は Award Day の後に決めることにしていた。
- 部品は 154 個ある。どれも `scripts/scene/parts.py`（Blender）で作り、一覧（`parts.json`）は Worker とアプリに同梱している。部品を足すには、デプロイとアプリのビルドが要る。
- 2026-10-21 の決定は、部品を「サーバーの Blender が、AI の書いたスクリプトで作る」としていた。この形は実装していない。注意として「AI が書いた Python を動かすので、ネットワークを切ったコンテナにする」とも書いていた。
- 部屋のスタートでの生成は「Claude 2 回で 10 秒まで」で、部品を作る時間は無い（[20261026-generate-scenes-in-room-on-start](./20261026-generate-scenes-in-room-on-start.md)）。その ADR は「苦手に合わせた出題」と「作った場面を長く残すこと（R2）」を、やらないこと（後で issue にする）にしていた。Award Day の当日は部屋の生成を止める（`SCENE_GENERATION` を `off`）。
- チームの Cloudflare の R2 は、11/14 の夜中に有効にした。binding `BUCKET`（バケット `ng-2622-bucket`）が main に入った（#135）。
- Cloudflare の無料プランでは、Worker の CPU は 1 回 10 ms まで（[Workers の limits](https://developers.cloudflare.com/workers/platform/limits/)）。Durable Object の CPU の上限は、[Durable Objects の limits](https://developers.cloudflare.com/durable-objects/platform/limits/) の表では 1 回 30 秒（既定）だが、同じページの FAQ は「Workers と同じ 1 回の CPU の上限」と書いており、チームのアカウントのプランでの値は確かめていない。Workers では文字列からコードを動かせない（`eval` 不可）。

## Context
- 苦手を練習する場面には、手持ちの部品に無い物が要ることがある。例えば、理由を言わせるには、見て分かる原因の物を置く必要がある。
- AI に Blender のコードを自由に書かせると、浮いた基本形・Blender の版の差・任意のコードの実行の危険が、全部生成の後に残る。
- 今の生成は 2 段目に部品の一覧を全部渡している。部品を作るたびに一覧が伸びるので、作った部品が増えるほど prompt が伸びて、いずれ破綻する。
- 作った部品をほかの人の場面にも出すなら、本人の話した中身が部品として残ったり、ほかの人に出たりしないようにしておく必要がある。
- 1 晩で作るので、新しいサーバー（コンテナ）や新しい有料プランを足す余裕は無い。

## Material for decision
- 前の調べ: repo の外の報告「3D部品の自動生成 ツール比較」（2026-11-13）。要点は次の 3 つ。
  - AI には `parts.py` の基本形と材質の名前だけを使う JSON の部品表を書かせ、決まった組み立て器で USDZ にするのがよい。出典は 3DCodeBench（[arXiv 2606.01057](https://arxiv.org/html/2606.01057v1)）。Claude が Blender のコードを書くと、1 回目に動く割合は 0.91、1 回に約 30 秒かかり、典型の失敗は「単純な基本形が宙に浮いた形」だった。
  - 自由なコードの実行は危ない。Blender MCP の `execute_blender_code` は CVE-2026-10688 になった。部品表なら組み立て器は `exec` をしない。
  - 待ち時間と費用の大半は LLM が占め、組み立ての道具の差は 3 ms〜1.5 秒で小さい。text-to-3D は、画像のテクスチャで返るので単色のパレットに合わない。
  - 調べは、組み立てを Containers の Blender に置く案を推した。決め手は「手作りの部品と AI の部品で組み立ての実装が 2 つになる」こと。既存の部品も TS に写すなら、この理由は消える。
- 手元の測定（2026-11-14、Apple M4、試作は repo の外）:
  - 依存の無い自前の TS（USDA の文字列＋64 バイト境界の無圧縮 zip）は、中央値くらいの部品を workerd で温まった状態 1.1〜2.6 ms、1 回目 7〜12 ms で組み、`usdchecker --arkit` を通った。
  - three.js は 7〜14 ms（1 回目 16〜18 ms）かかり、複数の材質を GeomSubset にする標準の書き方が `usdchecker` に落ちた。
  - 既存の 154 個は、Blender で基本形の呼び出しを記録すると部品表に写せた。三角形の数は全部一致し、TS で組み直した 5 個は外接箱が 1 mm 以内。部品表は中央値 26 行・2.4 KB、材質は 248 種。
- 今の 154 個の ID は、ほぼ「物は `名詞` か `名詞_区別`、人は `person_動作_誰_変種`、動物は `animal_動作_種類_変種`」の形になっている（`assets/parts/index.json`）。
- 設計の正本: [`docs/design/part-generation.md`](../design/part-generation.md)。
- 比べた案（組み立て）:

| 案 | 中身 | 良い点 | だめな点 |
| --- | --- | --- | --- |
| AI が Blender のスクリプトを書き、コンテナで動かす（2026-10-21 の決定） | 今の作り方をそのまま自動化する | 手作りと同じ Blender で作れる | 任意のコードを閉じ込める仕組みが要る。浮いた基本形が出やすい。コンテナと Workers Paid が要る |
| AI が部品表を書き、Containers の Blender が組む（前の調べの推し） | `parts.py` に JSON の読み口を足す | 手作りの部品と実装が 1 つ。コードの実行が無い | コンテナの運用と Workers Paid が要り、1 晩では立たない |
| AI が部品表を書き、Worker の three.js が組む | three.js の USDZExporter を使う | 今の backend に足すだけ | 遅い。複数の材質の書き方が `usdchecker` に落ちた |
| AI が部品表を書き、自前の TS が Durable Object の中で組む（採用） | USDA の文字列と無圧縮 zip を自分で書く | 依存が無く速い。今の backend に足すだけで、コンテナも有料プランも要らない（Durable Object の CPU の上限が無料プランで足りるかは確かめていない）。既存の部品も写せる | 基本形を TS で作り直す。既存の部品を切り替えるまでは、実装が Blender と TS の 2 つになる |
| アプリの RealityKit が部品表から組む | 端末で即時に組む | 待ちが無い | USDZ を前提にした今の仕組みと二重になる |

- 比べた案（部品の引き方）:

| 案 | 中身 | 良い点 | だめな点 |
| --- | --- | --- | --- |
| 一覧を prompt に出す（今） | 2 段目に部品の一覧を全部渡し、ID を enum で縛る | 一覧に無い ID は書けない | 作った部品が増えるたびに prompt が伸びる |
| ID の規約で書かせ、コードが引く（採用） | Claude は規約の形の ID を書く。有ればそのまま、人・動物は近いものに寄せ、物は無ければ作る | 部品が増えても prompt が伸びない | 同じ物に別の名詞が付くと二重に作る（別名の表か検索を後で足す） |
| ベクトル検索で候補を絞る | 英文から近い部品を探して渡す | 一覧を短くできる | 検索の置き場と学習が要り、1 晩では入らない |

- 比べた案（検査）: 形の検査だけ（採用。語彙と材質の enum、頼んだ寸法との差、浮いた基本形、三角形と op の上限）と、組んだ形を画像にして Claude に見せる検査。後者は、描画した画像を VLM に講評させても形を直す力が弱いという調べ（BlenderGym・P3D-Bench、前の調べの報告）と、待ちと費用が増えることから外した。
- 比べた案（作った部品の使い方）: みんなで即使う（採用）、作った本人の場面だけで使う、人が確かめてから使う。

## Decision
- 部品をその場で作るのは、苦手の分析から作る場面（`POST /weak-scenes`）のときだけにする。ふだんの練習は作り置きの場面で遊ぶ。部屋のスタートでの生成では作らない。
- AI（Claude）は部品表（JSON）だけを書く。組み立ては、依存の無い自前の TypeScript（USDA の文字列＋64 バイト境界の無圧縮 zip）が行う。three.js も Blender も、サーバーでは使わない。
  - 苦手の場面の生成の全部（Claude の呼び出し・部品の組み立て・R2 への書き込み・裏取りと座標の計算）は、1 回ごとに新しい Durable Object `WeakSceneMaker` の中で動かす。部品を作る部分は Durable Object を持たず、呼んだ側の CPU で組む。回数の上限は Worker が数える。
  - 既存の 154 個も部品表に写し、TS で作り直す。外接箱が 2 mm 以内で一致し、並べた画像で見分けがつかないことを確かめてから切り替える。時期は決めない。
- 検査は形だけにする（部品表の語彙と材質の enum、頼んだ寸法との差、浮いた基本形が無いか、三角形と op の上限）。AI に画像を見せる検査はしない。
- 作るのは物だけにする（category: `thing`・`furniture`・`food`・`plant`・`vehicle`）。人（`person`）・動物（`animal`）・地面（`ground`）・建物（`building`。壁・ドア・窓など）は作らない。
- 部品は ID の規約で引き、一覧を prompt に出さない。規約は、物は `名詞` か `名詞_区別`（`_` でつないで 3 語まで）、人は `person_動作_誰_変種`、動物は `animal_動作_種類_変種`（動作は省けることがある）。
  - 有ればそのまま使う。人・動物で無ければ、「誰」と「動作」が最も近いものに寄せる。物で無ければ、その ID で作る。
  - 今の一覧を出す生成も残す。部屋の生成と作り置きの生成の引き方は、スイッチ `SCENE_PART_LOOKUP` で選ぶ（既定は今の一覧を出す道）。この 2 つの生成では部品を作らない。
- 新しい部品は 1 場面 4 個まで（費用のヒューズ）にし、同時に作る。失敗した部品は 1 回だけ作り直し、それでもだめなら場面の生成を失敗として返す。
- 生成に渡すのは、級・苦手の種類・癖の題と直し方・次に試すことだけにする。本人の英文の引用は受けないし、渡さない。部品の ID は規約の形に縛り、人の名前・武器・暴力・性的な物は断る。刃物のうち、料理の道具や文房具（包丁・はさみなど）は作ってよく、剣・銃などの武器は断る。断ったときは、その物を使わない場面にする。
- 作った部品はみんなで使う。`id@版` で R2 に置き、検査を通ればすぐ使う。人の目の確かめは後から行い、悪い部品は版を上げて差し替える。
- 置き場は、チームの Cloudflare の R2 にする（binding `BUCKET`。本番は `ng-2622-bucket`、PR のプレビューは `ng-2622-bucket-preview`）。
  - 置く物は、部品の USDZ・メタデータ・部品表と、苦手の場面の配置（`weak-scenes/<sceneId>.json`）。
  - 部屋は、start の `sceneId` が `weak-` で始まれば、R2 から配置を読んで始める。部屋からアプリへ送る `room`・`round` には欄を足さない。
- Cloudflare のアカウントは無料プランのまま進める。merge の後に本番で何回か苦手の場面を作り、Observability で CPU の上限のエラー（1102 など）を数える。本番で CPU の上限で落ちることを確かめたら、有料プラン（Workers Paid、月 5 USD）を考える。落ちるのが全体の 1% 未満なら考えなくてよい（2026-11-14、リーダー）。
- 苦手の場面の口は、苦手の分析と同じ形で守る。IP ごとの 1 時間の回数と全体の 1 日の回数を上限にし、止めるスイッチ `WEAK_SCENE_GENERATION` を置く。Award Day の当日に部屋の生成を止める決まり（`SCENE_GENERATION` を `off`）は残す。
- 理由:
  - AI にデータだけを書かせれば、コードを閉じ込める仕組みも、Blender の版の差も要らなくなる。浮いた基本形は、組み立ての前にコードで見つけられる。
  - 自前の TS なら、今の backend のまま、コンテナも有料プランも足さずに 1 晩で入る。CPU の 1 回目の 7〜12 ms は Worker の 10 ms には危ないので、Durable Object の中で動かす。Durable Object の CPU の上限が無料プランでも 30 秒かは確かめておらず、FAQ のとおり 10 ms なら、有料プランか作りの見直しが要る。
  - ID の規約で引けば、作った部品が増えても prompt が伸びない。今の 154 個がすでにその形なので、新しい名前の付け方を覚えさせなくてよい。
  - みんなで使えば、同じ物を 2 度作らずに済み、部品が増えるほど作る数が減る。

## Consequences
- 良い面: 手持ちに無い物も、その人の苦手に合わせた場面に出せる。作った部品は次から誰の場面でも使え、部品を足すのにデプロイもアプリのビルドも要らない。
- 良い面: AI が書くのはデータだけなので、コードの実行の危険が無い。部品表を R2 に残すので、組み立て器を直せば同じ部品を作り直せる。
- トレードオフ: 既存の部品を切り替えるまでは、組み立ての実装が Blender（同梱の 154 個）と TS（作った部品）の 2 つになる。見た目が少しずれうる。
- トレードオフ: 人の目で確かめる前に、みんなの場面に部品が出る。悪い部品は後から版を上げて直すしかない。
- トレードオフ: 同じ物に別の名詞が付くと、二重に作る。別名の表か検索は後で足す。
- トレードオフ: 苦手の場面を作るたびに Claude を呼ぶ（場面の 2 段と、新しい部品 1 個ごとの部品表）。使われなかった場面の分は無駄になる。上限とスイッチで抑える。
- トレードオフ: 無料プランの Durable Object の CPU の上限を確かめないまま出す。上限が Workers と同じ 10 ms なら、苦手の場面の生成の一部が本番で落ちうる。落ちる割合を本番で数えて、有料プランにするかを決める。
- トレードオフ: 苦手の場面の生成には、級・苦手の種類に加えて、AI の分析の一部（癖の題と直し方・次に試すこと）を送る。これらはサーバーと Claude に渡るが、送った文字そのものはサーバーに残さない。R2 に残り続けるのは、それらから作った場面（見本の英文・チェックリスト・配置）と部品で、本人の英文の引用・表示名・端末の ID は含まない。ただし、癖の題や次に試すことに沿った中身は、場面の英文に表れうる。いつ消すかは決めていない。プライバシーポリシーを、この 3 つ（送る・IP で回数を数える・作った場面を R2 に置く）に合わせて直した。
- 部品を作るのは物だけなので、人と動物の動作は今の部品の中から寄せる。言える動詞は増えない。
